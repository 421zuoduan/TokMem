# TapMem 在切分边界不明确的开放式任务上的实验方案

> 这是面向论文讨论和实验实施的正文。重点是把实验为什么这样设计、数据怎么做、
> TapMem 和 TokMem 怎么训练、最后看什么结果说清楚。
>
> 更底层的概率推导、文件字段、哈希、伪代码和自动检查放在
> [复现细节文档](./2026-07-25-open-ended-ambiguous-boundary-experiment-technical.md)。
>
> 本文记录的是实验方案和数据审计结果，不是模型实验结果。

## 先说结论

我们建议用 **NL2Bash 做训练数据，InterCode-Bash 做最终测试**。

这个任务不是从一张预先写好的 API 表里选择工具。模型要根据自然语言要求，自己写出
Bash 命令，在 Docker 环境里执行，看到执行结果后还可以继续修改。因此，它比论文原来
的“按给定步骤调用工具”更开放。

整个实验只改“过程记忆从哪里来”，不改 TapMem 的基本做法：

1. 先把一条 Bash 命令拆成不会破坏语法的基本命令单元。

2. 从训练语料里找反复出现的相邻命令组合，把这些组合当成可能的过程片段。

3. 不给每条命令强行指定唯一切法，而是计算所有合法切法各有多大可能。

4. 训练时，在过程片段数量不变的前提下，抽取不同的切分位置。

5. TokMem、带 EOC 的 TokMem 和 TapMem 使用完全相同的训练样本、切分和训练顺序。

6. 测试时不给模型解析器、切分点、过程编号或参考命令，只看它能否完成环境中的任务。

这里没有“相邻表示变化分数”，也没有“长度固定为 1--4”“聚成 32 类”这类人为规定。

文中只保留几个论文和代码里无法避开的名称：

- `token`：模型内部使用的文本或控制标记编号；

- `EOC`：表示“当前过程片段到这里结束”的控制标记；

- `TCRA`：TapMem 中根据当前位置预测下一个过程记忆、并修正其生成分数的模块。

## 1. 这个实验要回答什么

评审的疑问可以改写成一句话：

> 如果任务里没有提前写好的原子步骤，而且一段程序可以有多种合理粒度，TapMem 还能
> 不能工作？

主比较是：

```text
TapMem - TokMem
```

两种方法都在“切分位置会变化”的训练数据上训练，最后比较 InterCode-Bash 完整
200 题、最多 10 轮交互的官方任务成功率。

只有同时满足下面两个条件，我们才认为主结果成立：

- 对 200 题做成对重抽样后，TapMem 相对 TokMem 的 95% 置信区间下界大于 0；

- 在两套预先固定的切分抽样表上，TapMem 对三个模型随机种子取平均后都优于 TokMem。

这项实验能支持的结论是：

> TapMem 的过程记忆不一定要对应人工给定的 API。它也可以对应从程序语料中学到的、
> 长度不固定的命令组合，并在训练切分点不唯一时继续发挥作用。

它不能证明：

- 模型找到了唯一、真实的人类步骤；

- TapMem 已经适用于所有开放世界任务；

- 测试中的每一种正确程序都与参考程序有相同结构；

- TapMem 自己在训练中精确求和了所有隐藏切分。

## 2. InterCode-Bash 是什么

InterCode-Bash 给模型一个自然语言任务和一个已经准备好的文件系统。模型每轮写一条
Bash 命令，环境执行后返回标准输出、错误信息和文件状态。模型最多可以尝试 10 轮。
评分看最终输出和文件系统状态，而不是要求模型逐字生成某一条参考命令。

例如，模型可能需要：

- 找出满足条件的文件；

- 对文本做筛选、排序和统计；

- 修改权限、移动文件或生成结果文件；

- 根据上一轮的报错换一种写法。

这正好补上原论文设置的两个缺口：

- 动作不是从一张固定工具表里选，而是自由生成 Bash；

- 一条命令内部哪些操作应当合成一个过程片段，没有现成答案。

我们仍把它称为“桥接实验”，因为训练和测试都在 Bash 领域内。它比结构化工具调用更
开放，但还不是网页、桌面、机器人等完全不同的领域。

## 3. 为什么这里的切分点不明确

考虑下面这条命令：

```bash
find /testbed -type f -print0 | sort -z | xargs -r0 md5sum | md5sum
```

从 Bash 语法看，它有四个顶层命令：

```text
find → sort → xargs → md5sum
```

但是“过程片段”可以有多种切法：

```text
[find + sort] [xargs + md5sum]
[find] [sort + xargs] [md5sum]
[find + sort + xargs] [md5sum]
[find] [sort] [xargs] [md5sum]
```

这些切法关注的粒度不同，但都不一定错：

- `find + sort` 可以看成“准备有序输入”；

- `sort + xargs` 可以看成“整理并交给下游程序”；

- 整条命令也可以看成一个完整的校验过程。

`bashlex` 只能告诉我们：

- 哪些位置是顶层命令；

- 管道符、重定向和引号在哪里；

- 每个语法节点在原字符串中的位置。

它不会告诉我们：

- 哪几个相邻命令构成一个可复用步骤；

- 哪个切分粒度最符合人的理解；

- 一个命令组合应该分配哪个 TapMem 记忆编号。

因此，本方案让解析器只负责“不要把 Bash 切坏”，让训练语料负责“哪些相邻组合值得
作为一个过程片段”。

还要注意，不能把所有表面上出现的程序名都当成顶层步骤。例如：

```bash
cd $(which python | xargs dirname)
```

顶层只有一个 `cd`。括号里的 `which` 和 `xargs` 属于命令替换，第一版实验不把它们
单独切出来。

同样：

```bash
find /testbed -name '*.php' -exec chmod 755 {} \; | wc -l
```

顶层只有 `find` 和 `wc`。`chmod` 是 `find -exec` 的参数内容，不是独立顶层步骤。

## 4. 实验数据怎么准备

### 4.1 数据来源

训练数据来自 [NL2Bash](https://github.com/TellinaTool/nl2bash)，最终测试来自
[InterCode-Bash](https://github.com/princeton-nlp/intercode)。

本地审计得到：

| 数据 | 数量 |
|---|---:|
| NL2Bash 原始自然语言—命令对 | 12,607 |
| 官方筛选后 | 9,305 |
| 官方 train/dev/test | 8,090 / 609 / 606 |
| `bashlex` 成功解析的原始命令（去泄漏前） | 12,466 |
| 语法上可用于第一版学习的原始命令（去泄漏前） | 12,196 |
| InterCode-Bash 正式测试题 | 200 |

InterCode 仓库里另有一个 24 题的 `test_queries.json`。它不是 200 题的子集，不能写成
“200 减去 24 等于 176”。主实验只报告四个文件系统分组组成的 200 题。

这里的 12,466、12,196、3,850 和 1,136 都只是对全部原始数据做语法检查得到的数字，
不是最终训练集大小。运行官方筛选、删除测试来源并限制命令结构后，必须重新报告最终
训练集和开发集各剩多少条。

### 4.2 先原样重放 NL2Bash 的官方筛选和划分

官方流程的顺序不能改：

1. 在完整 12,607 条数据上，以 `NUM_UTILITIES=100` 原样运行官方工具筛选脚本；

2. 得到 9,305 条筛选后数据；

3. 用官方固定随机种子 100 划分；

4. 得到 8,090 条训练、609 条开发、606 条测试数据。

脚本还会处理黑名单、灰名单和第 100 位同频等情况，不能自行简化成“严格保留恰好
100 个工具”。也不能先删掉测试集再运行筛选，因为那会改变工具频率，得到的就不是
官方数据划分。

官方旧脚本依赖较老的 Python 和 `bashlint`。我们会在固定镜像的 Python 3.9 容器中
重放一次，并保存：

- 原始文件和输出文件的哈希；

- 每个划分的行数和内容哈希；

- 12,607 条原始数据各自属于训练、开发、测试还是被筛掉的清单。

后续如果把脚本移植到 Python 3.10，输出必须与这次固定重放逐文件一致。只对上数量
不够。

### 4.3 防止训练数据泄漏到 InterCode

InterCode-Bash 是从 NL2Bash 任务进一步构造出来的。直接训练全部 NL2Bash 会把测试题
的来源样本带进训练集。

原始逐字比对已经发现：

| 重合方式 | InterCode 题数 |
|---|---:|
| 自然语言完全相同 | 25 |
| 参考命令完全相同 | 24 |
| 自然语言和命令都完全相同 | 23 |

因此，每一道 InterCode 题都必须追到具体的 NL2Bash 来源组。

我们先把 NL2Bash 原始行按三种关系连成“来源组”：

- 自然语言规范化后相同；

- Bash 命令逐字相同；

- 完整命令模板相同。

只要两条数据满足其中一种关系，就归入同一个连通组。组编号由组内所有样本编号排序后
计算哈希得到，不能人工命名。

文中还会用到“命令模板组”。它与来源组用途不同：

- 来源组把自然语言、完整命令和命令模板的重复关系都考虑进去，用于防止数据泄漏；

- 命令模板组只看 Bash 的程序、参数类型和语法结构是否相同，用于统计一个命令模式在
  多少种不同样本中出现，以及训练时按组平衡抽样。

对每道 InterCode 题，依次找：

1. 完全相同的自然语言和命令；

2. 自然语言或命令完全相同的候选；

3. 完整命令模板相同的候选；

4. 顶层工具和操作符序列相同，或只差一次插入、删除、替换的候选。

完全相同的自然语言—命令对，或者没有冲突、只指向一个来源组的确定性模板匹配，可以
自动确认。自动规则不能唯一确认的题，再由两名标注者分别查看候选组。只有两个人确认
的来源组有交集，才把交集记为最终来源；两人结论不同或只有一人确认，都算“来源未
确认”。主实验要求 200/200 题都能落到一个具体来源组。如果有一题只能找到“看起来
相近的样本”，却不能确认来源，200 题主实验就不能作为论文主要证据。

为了检查候选检索不是摆设，我们用已经知道来源的 23 个完全相同样本做盲测：

- 关掉逐字匹配和模板匹配，只靠工具/操作符序列检索，必须找回 23/23；

- 再把每条序列的第一个工具替换成语料中不存在的占位符，强制走“编辑距离为 1”的
  分支，也必须找回 23/23。

最终删除：

- 所有确认来源组；

- 所有检索到的保守候选组；

- 与 NL2Bash 官方测试集处在同一来源组的训练或开发样本。

删除后，同一个来源组只能出现在“清理后的训练集、清理后的开发集、NL2Bash 官方
测试集、InterCode 的候选或确认来源”四者之一。训练集和开发集要彼此隔离，而且都
不能与后两类测试来源重合。

清理后的训练集和开发集不能沿用原来的逐行划分，因为一个来源组可能曾经横跨两边。
具体做法是：合并清理后剩余的官方训练行和开发行，保留删除前已经算好的来源组编号，
再按来源组编号的 SHA256 哈希分桶。哈希前 8 字节转成整数后除以 10，余数为 0 的整组
进入开发集，其余整组进入训练集。这样大约是 90%/10%，同一来源组绝不会被拆到两边。

### 4.4 第一版使用哪些 Bash 命令

第一版只在下面两种命令上学习过程片段：

```text
一个顶层简单命令
或
command | command | ... | command
```

下面这些情况不进入第一版过程片段学习：

- 顶层 `list`、`if`、`for`、`while` 等复合结构；

- 管道中包含复合命令；

- heredoc；

- 多个顶层语法根；

- 空命令或只有注释。

它们只是从“学习过程片段的训练数据”中排除，不能从 InterCode 的 200 道正式测试题中
删掉。

去泄漏前，12,196 条原始候选命令的顶层基本单元数如下：

| 基本单元数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 命令数 | 8,346 | 2,714 | 747 | 254 | 91 | 34 | 8 | 2 |

其中 3,850 条至少有两个基本单元，1,136 条至少有三个。InterCode 的 200 条参考命令
也都能被 `bashlex` 解析，但这里只使用一个更宽的只读检查规则来确认文本能够还原，
不表示这 200 条都符合前面的“简单命令或平坦管道”训练规则。这套只读规则不参与过程
片段学习、训练目标生成或正式推理，正式测试也不会因为参考命令结构不同而删题。

本地审计已经对去泄漏前的 12,196 条原始语法候选和 200 条 InterCode 参考命令做过
字符、UTF-8 字节和 token 还原检查，失败数均为 0。正式去泄漏后仍要重新运行同一套
检查。

这个分布很重要：大多数命令只有一个基本单元。因此，后面不能只在少量长命令里制造
多种切分，然后声称整个训练过程都处理了模糊边界。

## 5. 怎么从 Bash 命令构造过程片段

### 5.1 先得到基本命令单元

对于简单命令，整条命令就是一个基本单元。

对于平坦管道，管道两侧的每个顶层 `command` 是一个基本单元。例如：

```bash
find . -type f | sort | head -n 10
```

得到三个基本单元：

```text
START:find
PIPE:sort
PIPE:head
```

每个基本单元只保留两个用于学习的标识：

```text
进入它之前的连接方式 + 顶层程序名
```

连接方式包括：

- `START`：整条命令的第一个单元；

- `PIPE`：由普通管道 `|` 接入；

- `PIPE_STDERR`：由 `|&` 接入。

程序名从 Bash 语法树中第一个静态命令词得到，并做确定性处理，例如去掉固定路径，
`/usr/bin/sort` 记为 `sort`。如果一个静态程序名在清理后训练集中只出现在不到两个
命令模板组里，就按前面的连接方式记成专门的“低频程序”标识；如果程序名是动态计算
出来的，就记成对应连接方式下的“未知程序”标识。这两类标识及所有单基本单元都必须
保留，后面不能删。

这个过程不调用大模型，也不让大模型判断语义。

原始空格、引号、管道符和注释不会丢失。我们另外保存每个基本单元在原字符串中的字符
范围，使任何切分删除记忆标记后都能逐字还原原命令。

### 5.2 候选过程片段从哪里来

一个候选过程片段，就是训练命令中连续出现的一段基本单元。

长度大于 1 的候选必须同时满足：

- 至少在两个不同命令模板组中出现；

- 至少有一次只是较长命令的一部分，而不是永远覆盖整条命令。

例如：

```text
[START:find, PIPE:xargs]
```

如果它在多个不同命令模板中出现，而且至少有一次后面还有 `wc`、`sort` 等命令，就可以
进入初始候选表。

这里不设“最长只能包含 4 个基本单元”。最长长度由训练语料真实长度决定。实现时直接
统计不重复的连续组合，不把所有重叠位置展开成大量独立样本。

去泄漏前的本地审计结果是：

| 项目 | 数量 |
|---|---:|
| 顶层程序名在官方允许表中的可用命令 | 11,379 |
| 单基本单元类型 | 193 |
| 在至少两条命令中重复的多单元组合 | 782 |
| 同时满足“至少一次为较长命令的一部分” | 550 |

最终数量必须在去泄漏后的训练集上重新统计。

### 5.3 一个短片段和一个长片段可以同时保留吗

可以。

例如下面三个候选可以同时在过程片段表里：

```text
[find]
[find + xargs]
[find + xargs + wc]
```

它们代表不同粒度。真正给一条命令切分时，同一个基本单元只能被一个片段覆盖，因此这些
候选会在“完整切分方案”之间竞争，不会在同一切分中重叠使用。

### 5.4 不再计算“变化分数”，而是给完整切分打分

设一个过程片段 \(v\) 在训练语料中学到的概率为 \(\theta_v\)。所有片段的概率都大于
0，加起来等于 1。模型还学习一个介于 0 和 1 之间的结束概率 \(\rho\)。

把一条完整切分按顺序写成 \(B=(v_1,\ldots,v_J)\)，其中 \(J\) 是这次切分使用的片段
数。它的分数是：

$$
s(B)
=
\log\rho
+J\log(1-\rho)
+\sum_{j=1}^{J}\log\theta_{v_j}.
$$

这三个部分分别表示：

- 最后结束；

- 连续生成了 \(J\) 个过程片段；

- 这 \(J\) 个片段各自在训练语料中有多大可能。

例如：

```text
[find+xargs] [wc]
```

和：

```text
[find] [xargs+wc]
```

会因为其中各个过程片段的训练概率不同而得到不同分数。

这不是“看相邻向量变化大不大”，也不使用句向量、余弦相似度或大模型语义打分。

### 5.5 怎么学到这些概率

对每条训练命令，我们先列出所有能够从头到尾完整覆盖它的合法切分。

然后反复做两步：

1. 根据当前概率，计算每个候选片段在所有完整切分中预计会被使用多少次；

2. 根据这些预计次数更新每个片段的概率和结束概率。

计算时使用动态规划，不需要暴力列出指数数量的切分。动态规划会把所有合法完整切分都
算进去，不只保留前三个。

训练时不是每一行权重都相同。同一个命令模板组的总权重固定为 1；如果组内有 \(n_g\)
条自然语言改写，每条权重就是 \(1/n_g\)。这样，某个命令模板有很多近似改写时，不会
仅靠重复次数把它的片段概率抬高。

为了避免某些必须保留的未知类型概率变成严格的 0，每个过程片段加
\(10^{-8}\) 的固定小计数。我们用三种固定初始值分别训练：

- 按它出现在多少个模板组中初始化；

- 全部均匀初始化；

- 按“模板组数量 × 片段长度”初始化。

每种初始值都走完整的删减流程。对每一个候选容量 \(K\)，比较三条路径在训练集上的
目标值：这个目标值就是训练数据的总对数概率，再加上前述 \(10^{-8}\) 小计数对应的
平滑项。取目标值最高的一条交给开发集；如果完全相同，就取过程片段表哈希值按字节排序
最小的一条。三条路径各自的结果仍要全部报告，不能只展示最后被选中的一条。

### 5.6 候选太多时怎么删

模型最多有 248 个预留控制标记。TapMem 还要占用一个 EOC，因此过程片段最多保留：

$$
K_{\max}=247.
$$

把所有必须保留的单基本单元、低频程序和未知程序类型数量记为 \(K_{\min}\)。必须先
检查 \(K_{\min}\le247\)；否则当前数据表示法已经超过模型容量，本次构造直接失败，
不能看过测试结果再临时合并类型。

所有这些必须保留的类型不能删除。对于其他多单元候选，做下面的检查：

1. 暂时删除候选 \(v\)；

2. 其他片段的概率重新归一化，但结束概率保持不变；

3. 重新计算整个训练集的总对数概率；

4. 用删除前后的差值衡量“当前参数下删掉它会损失多少”。

这个量只用于删候选，不能把它叫作切分点的“变化分数”。在
\(K_{\min}\le247\)、当前总片段数 \(K>247\)、且至少还有一个候选可删的前提下，设
当前可删除候选数为 \(n_{\mathrm{可删}}\)，本轮实际删除：

$$
n_{\mathrm{删}}
=
\min\left(
\max\left(1,\left\lfloor0.2n_{\mathrm{可删}}\right\rfloor\right),
K-247
\right).
$$

也就是说，通常删除可删候选数向下取整后的 20%；不足一个时删一个；接近 247 时只删
到 247，绝不跨过去。每轮删除后都重新训练概率。数量准确到 247 后，每次只删一个，
并为每个整数 \(K\) 保存一套模型。

### 5.7 最后保留多少个过程片段

\(K\) 表示 TapMem 记忆库容量，不表示世界上存在 \(K\) 个真实步骤。

每个候选 \(K\) 只在训练集上拟合，然后在 NL2Bash 开发集上计算：

```text
平均每个基本单元的负对数概率
```

开发集中的同一命令模板组总权重为 1，避免大量改写句子把结果拉偏。

选择方法是：

1. 先用完整开发集找到负对数概率最低的 \(K_{\mathrm{best}}^{\mathrm{full}}\)，之后固定
   它不变；

2. 对命令模板组做 1,000 次有放回抽取。每一次都用同一批抽到的模板组计算所有 \(K\)，
   不能给不同 \(K\) 抽不同数据；

3. 把第 \(b\) 次抽取算出的开发集得分记为 \(D^{(b)}(K)\)。计算每个 \(K\) 与固定
   \(K_{\mathrm{best}}^{\mathrm{full}}\) 的差：

   $$
   d_K^{(b)}
   =
   D^{(b)}(K)
   -
   D^{(b)}(K_{\mathrm{best}}^{\mathrm{full}}).
   $$

4. 用这 1,000 个差值的标准差作为 \(se(d_K)\)。再在完整开发集上计算对应差值
   \(d_K^{\mathrm{full}}\)，从小到大选第一个满足
   \(d_K^{\mathrm{full}}\le se(d_K)\) 的 \(K\)。

每次重抽样都不能重新挑一个“当次最好”的 \(K\)，否则比较基准会来回变化。

这样做的目的是：在开发集效果没有明显变差时，优先使用更小的记忆库。InterCode 的
参考命令、测试成功率或测试结构都不能参与 \(K\) 的选择。

## 6. 怎么构造“切分点会变化”的训练数据

### 6.1 先确定概率最高的切分

对于每条命令，用上面的完整切分分数找出概率最高的切分。技术文献常把“概率最高”
简称为 MAP，因此这里把它记为 \(B_{\mathrm{MAP}}\)。后文出现 MAP 时，都只是指
“概率最高的固定切分”。

如果两个切分分数完全相同，固定按下面顺序决定：

1. 过程片段更少的优先；

2. 仍相同时，把每个可切位置从左到右写成 0/1 串，`1` 表示切、`0` 表示不切，
   选择按字典顺序最小的 0/1 串；

3. 最后选择按字典顺序最小的过程片段编号序列。

这个规则必须由训练数据生成、检查脚本和抽样脚本共同使用，不能依赖代码遍历顺序。

### 6.2 主设置只改变切分位置，不改变片段数量

设概率最高的切分用了 \(J_{\mathrm{MAP}}\) 个过程片段。

主设置只在“同样使用 \(J_{\mathrm{MAP}}\) 个片段”的合法切分中抽样：

$$
q(B\mid x,J=J_{\mathrm{MAP}})
\propto
\prod_{v\in B}(1-\rho)\theta_v.
$$

后文还要判断一条命令是不是“实际上只有一种切法占绝对优势”。为此，在这些相同片段数
的合法切分中，用下面的数表示有多少种切法真正占有可见概率：

$$
N_{\mathrm{有效}}(x)
=
\exp\left(
-\sum_B q(B\mid x,J_{\mathrm{MAP}})
\log q(B\mid x,J_{\mathrm{MAP}})
\right).
$$

如果所有概率都压在一种切法上，这个数接近 1；如果两种切法各占一半，这个数等于 2。
第 13 节所说的“有效切法数至少 1.5”就是这个数，不是简单数一共有多少种合法切法。

实际实现仍使用动态规划：

1. 计算从开头到每个位置、恰好使用若干片段的总概率；

2. 从命令末尾开始，按这些概率反向抽取上一段；

3. 直到回到开头，得到一条完整切分。

这样，抽样切分和最高概率切分具有完全相同的：

- 过程片段数量；

- 记忆标记数量；

- EOC 数量；

- TapMem 下一过程选择的训练位置数量；

- 普通 Bash token。

唯一变化的是切分点在哪里，以及每段对应哪个过程记忆。

因此，随机切分与概率最高切分的差异不能简单解释成“随机切分看到了更多 EOC”或
“有更多下一过程选择训练”。

### 6.3 训练中到底有多少样本真的换了切分

不能只报告“长命令里有多少种切法”。我们直接统计所有训练展示次数中，抽样切分是否与
最高概率切分不同：

$$
R_{\mathrm{changed}}
=
\frac{
\text{抽样切分与最高概率切分不同的训练展示次数}
}{
\text{全部训练展示次数}
}.
$$

分母包括：

- 只有一个基本单元的命令；

- 在固定片段数量下只有一种切法的命令；

- 虽然有其他切法，但这次又抽回最高概率切分的命令。

所以这个比例不能靠只看 \(L\ge3\) 的小子集做高。

还要从最终生成的训练 token 中计算三种加权比例：

- 非最高概率切分贡献的自回归监督 token 数，占全部自回归监督 token 的比例；

- 非最高概率切分中的 EOC 数，占全部 EOC 的比例；

- 非最高概率切分中的下一过程选择位置数，占全部这类位置的比例。

分子和分母都必须从最终训练目标中逐项计数，不能按字符长度估算。

主实验使用两个固定抽样种子 `1729` 和 `7919`。两套训练数据都必须满足：

```text
R_changed >= 0.10
```

不能不停更换随机种子直到通过。

上面的比例反映“模型训练时实际接触了多少边界变化”。我们还要在没有 A/R 平衡抽样的
原始训练分布上，计算每条命令抽到非最高概率切分的平均概率。这个数字反映语料本身的
边界不确定程度。两者必须分开报告，不能把人为设成 50% 的 A 组训练占比说成自然语料
中有 50% 的命令边界不明确。

### 6.4 防止重复少数命令把比例做高

先定义“边界变化比较明显”的训练样本：

- 最高概率切分至少有两个过程片段；

- 在相同片段数量下至少有两种合法切法；

- 其他切法的总概率至少为 0.25。

把含有这类样本的命令模板组记为 A 组，其余模板组记为 R 组。

A 组必须满足：

$$
|A|
\ge
\max(100,\lceil0.20\times|L\ge3\text{ 的模板组}|\rceil).
$$

R 组也必须至少有 100 组。

每个训练周期从 A、R 两边各取相同数量的不同模板组。每边取多少组固定为：

$$
M
=
2\left\lfloor
\frac{\min(|A|,|R|)}{2}
\right\rfloor.
$$

因此一个训练周期共有 \(M/2\) 个有效批次和 \(2M\) 次训练展示。每个有效批次固定放：

```text
2 个 A 组样本 + 2 个 R 组样本
```

1B 直接用 4 条样本组成这个有效批次；8B 每次只放 1 条，连续累积 4 次后再更新参数。

每个训练周期内：

- 同一命令模板组最多出现一次；

- 两边都按固定哈希顺序无放回抽取；

- A 组只能从该组中真正满足前述三个条件的样本里选，不能轮换到同组中边界变化不明显
  的样本；

- R 组可以从组内全部样本中选；两组在各自允许的样本范围内，跨训练周期按稳定样本编号
  轮换使用。

还要报告：

- A/R 组各有多少组；

- 每组在三轮训练中出现多少次；

- 出现最多的组占全部训练展示的比例；

- 有效参与训练的组数量。

这样可以防止只重复一两个高不确定命令，就把 \(R_{\mathrm{changed}}\) 做到 0.10 以上。

## 7. 怎么生成 TokMem 和 TapMem 的训练目标

假设一次抽样得到：

```text
[a1+a2] [a3]
```

对应两个过程片段编号 `v12` 和 `v3`。

TokMem 的目标是：

```text
<m_v12> 原始片段12
<m_v3>  原始片段3
<回复结束>
```

带 EOC 的方法是：

```text
<m_v12> 原始片段12 <EOC>
<m_v3>  原始片段3  <EOC>
<回复结束>
```

TapMem 在相同训练目标上增加 TCRA：它在回复开头，以及后面确实还接有下一段的 EOC
位置，预测下一个过程记忆。最后一个 EOC 后是回复结束标记，不计为下一过程标签。

### 7.1 如何保证不同切分没有偷偷改掉 Bash

每条原始命令先按固定字符范围切成基础文本块，再用模型的分词器分别转成 token 编号。

所有切分方案只能在这些固定块之间分组，不能重新编码或移动原始字符。因此，同一命令的
不同切分在删掉记忆标记和 EOC 后，普通 Bash token 编号必须逐项完全相同。

自动检查要求：

- 字符合并后与原始命令逐字相同；

- UTF-8 字节哈希相同；

- 普通 token 编号相同；

- 每个基本单元恰好被覆盖一次；

- 没有字符或 token 重叠、遗漏。

### 7.2 三种方法必须共享什么

TokMem、带 EOC 的 TokMem 和 TapMem 必须共享：

- 同一过程片段表和编号；

- 同一训练样本展示顺序；

- 同一条样本的同一切分；

- 同一普通 Bash token；

- 同一模型随机种子；

- 同一训练轮数、学习率、批大小和上下文长度。

固定切分实验和随机切分实验也必须逐条使用同一份训练展示清单；它们只能在同一条命令
采用哪种切分上不同，不能使用不同的模板组或样本顺序。

抽样种子只决定切分；模型种子只决定可训练参数初始化和训练随机性。不能把三个模型种子
说成三套独立切分数据。

### 7.3 训练目标的准确说法

每当一条命令被选入某个训练周期，就按预先生成的切分表为这次训练展示取一个切分，再对
带记忆标记的目标做普通自回归训练。并不是每条命令在每个训练周期都会出现。

因此，准确说法是：

> 在一套固定的切分概率下，用随机切分版本做训练增强。

不能写成：

> TapMem 在训练中对所有隐藏切分做了精确求和。

过程片段概率在预处理阶段训练完毕，TapMem 不会反向修改它。

## 8. 固定训练设置

第一次在 InterCode 200 题上运行候选模型之前，下面的设置全部冻结：

三种方法都冻结基础模型，不使用 LoRA、其他适配层、外部检索器，也不在测试时继续训练。
TokMem 只训练过程记忆标记；带 EOC 的方法再训练 EOC；TapMem 再训练 TCRA。

| 设置 | Llama-1B 主实验 | Llama-8B 确认实验 |
|---|---:|---:|
| 模型 | Llama-3.2-1B-Instruct | Llama-3.1-8B-Instruct |
| 训练轮数 | 3 | 3 |
| 学习率 | \(5\times10^{-3}\) | \(5\times10^{-3}\) |
| 优化器 | AdamW，\(\beta=(0.9,0.999)\)，\(\epsilon=10^{-8}\)，权重衰减 0 | 相同 |
| 学习率变化 | 前 10% 步数预热，之后线性降到 0 | 相同 |
| 单次放入显卡 / 累积次数 | 4 / 1 | 1 / 4 |
| 有效批大小 | 4 | 4 |
| 训练精度 | bfloat16 | bfloat16 |
| 最大训练长度 | 1024 token | 1024 token |
| 普通生成损失 | 对回复中所有被监督 token 取平均 | 相同 |
| TCRA 损失权重 | 0.1 | 0.1 |
| TCRA 选择头 | 线性层；分类时不把梯度传回边界隐藏状态 | 相同 |
| 训练时是否把 TCRA 分数加到记忆分数 | 是 | 是 |
| TCRA 对记忆生成分数的修正倍数 | 1.0 | 1.0 |
| 生成方式 | 贪心生成 | 贪心生成 |
| 每轮最多生成 | 512 token | 512 token |
| 交互历史上限 | 8192 token | 8192 token |
| 保存哪个模型 | 第 3 轮最后一步 | 第 3 轮最后一步 |

不搜索学习率、训练轮数、TCRA 权重、生成温度，也不从多个训练中间保存点里挑最有利
的一个。

所有方法用同一个模型种子和同一套正交初始化办法生成过程记忆参数。某次训练如果出现
非有限损失或梯度，导致任何参数更新被跳过，这次运行直接记为失败，不能改用更早的模型
保存点。

任何训练目标超过 1024 token，数据构造都直接失败；不能让不同方法各自截掉不同样本。

如果交互历史超过 8192 token：

1. 始终保留系统提示、原始任务和最新观察；

2. 从最早开始，整轮删除“上一条命令 + 对应观察”；

3. 三种方法使用同一删除清单。

## 9. 测试时模型能看到什么

测试输入只有：

- 原始任务说明；

- 模型前几轮真正执行过的 Bash；

- 环境返回的输出、错误和文件状态；

- 剩余轮数和提交规则。

测试时不运行过程片段模型，也不给：

- Bash 解析结果；

- 参考命令；

- 参考命令里的工具名；

- 正确切分点；

- 正确过程记忆编号。

模型自己生成：

```text
记忆标记 → Bash 片段 → EOC → 下一个记忆标记 → ...
```

送入 Docker 前，运行器只做三件事：

1. 在第一个完整回复结束标记处截断；

2. 按精确 token 编号删除过程记忆标记和 EOC；

3. 把剩余普通 token 解码成 Bash。

运行器不能：

- 模糊替换字符串；

- 自动补引号、路径、管道或参数；

- 根据参考答案修命令；

- 解析失败后自动改写。

每个“任务 × 方法 × 切分种子 × 模型种子”使用独立、完全重置的 Docker 容器。下一轮
历史只回放真正执行过的 Bash 和环境观察，不回放模型内部的记忆标记。

所有方法还必须逐字使用相同的提示词、停止和提交规则、环境输出截断规则，以及历史
超长时的删除清单。这些文本和规则都在第一次正式测试前保存哈希。

## 10. 实验怎么跑

### 10.1 Llama-1B 主实验

| 训练设置 | TokMem | 带 EOC | TapMem | 随机种子 |
|---|---:|---:|---:|---|
| 概率最高固定切分 | ✓ | ✓ | ✓ | 模型 `{40,41,42}` |
| 相同片段数下随机切分 | ✓ | ✓ | ✓ | 切分 `{1729,7919}` × 模型 `{40,41,42}` |
| 每个基本单元单独成段 | ✓ | - | ✓ | 模型 `{40,41,42}` |
| 在已保留的过程片段表中，与 MAP 段数相同的合法切分等概率抽样 | ✓ | - | ✓ | 切分 `1729` × 模型 `{40,41,42}` |

“每个基本单元单独成段”只是一个原子步骤参考。它使用的记忆数量和 TCRA 参数量与主设置
不同，因此不能把两者性能差直接解释成“多命令过程片段带来的因果收益”。

这个等概率对照保留相同的过程片段表，并固定使用与 MAP 相同的片段数，只把这些合法
切分之间的概率改为相等。它只检查结果是否依赖语料学到的片段概率，不能代表对所有语法
位置任意切分。

### 10.2 Llama-8B 确认实验

只跑最关键设置：

```text
相同片段数下随机切分
TokMem / 带 EOC / TapMem
切分种子 1729
模型种子 40、41、42
完整 200 题
```

### 10.3 检查结果是否依赖某一个记忆库大小

除了报告开发集上所有 \(K\) 的曲线，还要在 1B 随机切分设置中检查三个容量：

$$
\max(K_{\min},\hat K-16),\qquad
\hat K,\qquad
\min(247,\hat K+16).
$$

\(K_{\min}\) 是所有必须保留的单基本单元和未知类型数量，\(\hat K\) 是开发集最终选中的
容量。三个容量都固定使用切分种子 `1729`、模型种子 `42`，分别训练 TokMem 和
TapMem。这个检查只用于判断结果是否稳定，不能反过来修改主实验的 \(\hat K\)。

### 10.4 正式运行顺序

1. 重放官方数据划分并完成去泄漏；

2. 解析 Bash，生成基本单元；

3. 学习过程片段表，选择 \(K\)；

4. 生成两套切分表和实际变化统计；

5. 完成所有逐字还原和 token 一致性检查；

6. 在自建的 24 个合成 Docker 小任务上检查运行器；

7. 冻结提示词、运行器、训练设置和文件哈希；

8. 运行 1B 主实验；

9. 运行对照实验和 8B 确认实验；

10. 训练前读取的测试参考程序只用于第 4.3 节的来源追溯；模型、过程片段表、\(K\)、
    提示词和测试规则全部冻结后，才允许再次使用参考程序的语法结构做探索性分析。

## 11. 看哪些结果

### 11.1 主结果

完整 200 题、最多 10 轮：

- 官方二元任务成功率；

- `TapMem - TokMem` 的成对差值；

- 10,000 次按任务重抽样得到的 95% 置信区间；

- 六个“切分种子 × 模型种子”配对实验各自的差值；

- 两个切分种子各自的三模型种子平均差值；

- TapMem 赢、输、打平的题数。

具体计算方法是：对任务 \(i\)，先在两个切分种子和三个模型种子组成的六组配对运行中，
计算 TapMem 成功结果减去 TokMem 成功结果，再取平均：

$$
d_i
=
\frac{1}{6}
\sum_{d\in\{1729,7919\}}
\sum_{s\in\{40,41,42\}}
\left(y_{i,d,s}^{Tap}-y_{i,d,s}^{Tok}\right).
$$

然后以“任务”为单位，从 200 个 \(d_i\) 中有放回抽取 200 个，重复 10,000 次，
报告平均差值的 2.5% 和 97.5% 分位数。

不能把 `200 × 6` 当成 1,200 个独立样本。这个区间只说明六组预先固定的
TapMem–TokMem 配对运行在这 200 个任务上的平均差异，不代表任意模型初始化或任意
切分表。两个切分种子也不足以可靠估计“所有可能切分表”的总体方差，因此不做多层
重抽样，而是单独报告两套切分表各自的三种子平均差值，并要求两者都大于 0。

### 11.2 辅助结果

- 单轮成功率；

- 官方连续奖励；

- 产生非法命令或环境错误的比例；

- 平均用了多少轮；

- 第一轮是否成功；

- TokMem 和 TapMem 第一轮都失败的共同任务中，谁在第 10 轮前恢复成功；

- 固定切分与随机切分的差异；

- 带 EOC 的 TokMem 相对普通 TokMem 的差异；

- TapMem 相对带 EOC 方法的差异。

有多项辅助比较时，统一使用 Holm 方法校正显著性门槛，避免“比较得越多，越容易偶然
挑中一个好结果”；或者把这些比较明确标为探索性结果。不能在看完结果后，从中挑最有利
的一项改成主结论。

最后一项只能说明“完整 TCRA 模块有没有额外价值”。TapMem 还多了一个线性选择头，
所以不能仅凭这个差值证明收益一定来自隐藏状态条件化，而不是额外参数。

如果要声称 TapMem 更会利用执行反馈，还需要额外做“屏蔽环境观察”的对照。否则只能写：

> TapMem 在提供执行反馈的交互环境中成功率更高。

不能写：

> 已经证明 TapMem 更善于理解和使用反馈。

## 12. 人工检查：这些切分点是否真的不唯一

从去泄漏后的 NL2Bash 开发集里，按固定样本编号随机抽 100 条至少含三个基本单元的命令。
不能按模型认为“最不确定”的样本挑选。如果合格命令不足 100 条，就全部使用，并把实际
命令数记为 \(C\)。

三名熟悉 Bash 的标注者独立看到：

- 自然语言任务；

- 完整原始命令；

- 语法允许切分的位置；

- 一句话说明：“一个可复用执行阶段在哪里结束，下一个阶段在哪里开始？”

标注者可以：

- 不切，整条命令作为一个阶段；

- 选择一个或多个合法切分点；

- 写一句理由。

他们看不到模型切分、片段编号、建议段数或其他人的答案。

### 12.1 计算什么

对每个可切位置，三个人中有多少人选择它，记为 0、1、2 或 3。

报告：

- 只有 1 人或 2 人选择的切分点比例；

- 三人整条切分完全一致的命令比例；

- 标注者两两之间的边界精确率（Precision）、召回率（Recall）和 F1；

- 扣除偶然一致后，三个人整体有多一致（Fleiss' \(\kappa\)）；

- 每个人通常把命令切成几段；

- 模型给出的切分概率与三人投票比例之间的均方误差（Brier 分数）；

- 模型对“不确定位置”的排序是否与人类分歧大小一致（Spearman 相关）。

为了避免“模型和人都不确定，所以看起来相关”的空结论，再比较两个简单基准：

1. 对当前命令，把其他 \(C-1\) 条命令的“切分票数总和 ÷ 可切位置总数”作为它所有
   位置的固定预测值；

2. 不看过程片段表，只对这条命令全部 \(2^{L-1}\) 个不破坏语法的 0/1 切分方案等概率
   取值。由于每个位置都有切或不切两种选择，所以每个位置的预测值都是 0.5。

计算 Brier 分数时，先在每条命令内部对所有可切位置取平均，再对 \(C\) 条命令取平均，
避免可切位置多的长命令占过大权重。然后以“整条命令”为单位做 10,000 次成对重抽样，
计算：

```text
简单平均切分率的 Brier 分数 - 模型的 Brier 分数
```

这个差值的 95% 置信区间下界必须大于 0。

Spearman 相关虽然使用所有可切位置计算，但置信区间也必须每次重抽整条命令，并在每次
重抽后重新计算相关，不能把同一命令里的各个位置当成彼此独立的样本。它的 95% 置信
区间下界也必须大于 0。否则只能把训练数据称为：

```text
由语料统计产生的随机切分版本
```

不能称为“人也认为合理的不同过程边界”。

## 13. 哪些结果意味着实验没有回答评审问题

下面的标准都必须在查看 InterCode 模型结果之前确定。

### 13.1 数据泄漏没有处理干净

出现任一情况，主实验无效：

- 200 道 InterCode 题中有任何一道找不到具体 NL2Bash 来源组；

- 已知来源的两种检索盲测没有达到 23/23；

- NL2Bash 官方测试来源组，或 InterCode 的任一检索候选组和确认来源组，仍进入训练、
  开发、过程片段学习或 \(K\) 选择；

- 去泄漏后，训练和开发之间仍有相同自然语言、完整命令或完整命令模板；或者清理后的
  训练/开发数据与任一 InterCode 候选或确认来源仍有完整命令或完整命令模板重合。

### 13.2 训练数据没有形成足够的可变长度和边界变化

出现任一情况，不能把它称为有效的模糊边界实验：

- 最终多基本单元过程片段少于 25 个；

- 多基本单元过程片段覆盖的训练基本单元少于 25%；

- 未知或低频程序名占训练基本单元超过 10%；

- 在至少有两个基本单元的命令中，概率最高切分仍有至少两个过程片段的比例低于 50%；

- A 组少于 100，或少于至少含三个基本单元的模板组的 20%；

- R 组少于 100；

- 在至少含三个基本单元的命令中，同时满足“概率最高切分至少两段”和“按切分概率折算
  的有效切法数至少为 1.5”的命令比例低于 25%；

- 任一切分种子的 \(R_{\mathrm{changed}}<0.10\)。

### 13.3 人工检查不支持“存在多种合理切分”

出现任一情况，只能把这些数据称为“由语料统计产生的随机切分版本”：

- 存在分歧的切分点少于 20%；

- 超过 80% 的命令三人整条切分完全一致；

- 模型切分概率没有显著优于简单平均切分率；

- 模型认为不确定的位置与人类分歧位置没有显著正相关。

### 13.4 模型结果不支持主结论

出现任一情况，不能声称 TapMem 在模糊边界设置中优于 TokMem：

- TapMem 相对 TokMem 的主置信区间下界不大于 0；

- 任一切分种子下，TapMem 的三模型种子平均结果不优于 TokMem；

- 两种方法的平均成功率都低于 5% 或都高于 95%，形成明显地板或天花板；

- 只有记忆编号或 EOC 预测更准，但官方任务成功率没有提高；

- TapMem 只在固定切分上提高，在切分会变化时不提高；

- 提升方向随着模型种子或记忆库大小检查而反转，此时结果应标为不稳定。

### 13.5 对照实验限制了能说的话

- 如果带 EOC 的 TokMem 已经解释全部收益，而 TapMem 不再优于它，只能说“显式结束
  标记有帮助”，不能说 TCRA 还有额外价值；

- 如果“在已保留的过程片段表中，与 MAP 段数相同的合法切分等概率抽样”对照与学到的
  切分概率一样好或更好，只能说收益不依赖训练语料学到的片段概率，不能声称这些概率
  挑出了更合理的切分；

- 如果没有屏蔽环境观察的对照，不能作“TapMem 更会利用执行反馈”的因果结论。

这些标准都必须在查看 InterCode 模型结果前写入配置，不能根据结果临时调整。

## 15. 必须自动检查什么

数据准备阶段：

- 官方重放数量必须是 `12607 → 9305 → 8090/609/606`；

- 官方输出文件、内容集合和逐行归属必须与固定重放一致；

- 200/200 题都有具体来源组；

- 两种已知来源检索都达到 23/23；

- NL2Bash 官方测试来源组，以及 InterCode 的全部候选组和确认来源组，进入训练、
  开发、过程片段学习或 \(K\) 选择的数据行数都为 0；

- 训练、开发、官方测试和 InterCode 候选/确认来源四类来源组两两不重合；

- 正文所有最终训练/开发数量都由去泄漏后的清单重新计算，不能沿用 12,196。

Bash 和 token 阶段：

- 基本单元按原字符串顺序排列且不重叠；

- 基本单元、间隔和前后缀合并后逐字还原 Bash；

- 每个切分覆盖全部基本单元且没有重复；

- 删除记忆标记和 EOC 后，所有切分的普通 token 编号完全相同；

- 只做 `bashlex` 和 `bash -n` 语法检查，绝不在宿主机执行训练命令。

概率和抽样阶段：

- 在小型人工例子上，动态规划结果与穷举所有切分完全一致；

- 最高概率切分的并列处理规则一致；

- 抽样得到的过程片段数始终等于 \(J_{\mathrm{MAP}}\)；

- 两个切分种子都满足 \(R_{\mathrm{changed}}\ge0.10\)；

- 每个有效批次确实是 2 个 A 组和 2 个 R 组；

- 同一模板组每个训练周期最多出现一次。

训练目标阶段：

- 三种方法使用相同的训练展示编号和切分编号；

- 概率最高固定切分与随机切分实验的训练展示编号也逐条完全相同；

- 从“切分表与 token 数表连接计算”和“直接重新解析最终训练目标”两条独立路径得到的
  token/EOC/下一过程位置统计逐整数一致；

- 训练展示表中的 `presentation_id` 唯一，切分表中的
  `(presentation_id, data_seed)` 唯一，训练目标表中的
  `(presentation_id, data_seed, method)` 唯一；

- 固定 `data_seed` 和 `method` 后连接三类文件时没有缺失或一对多。总体上，一个训练
  展示本来就应对应两个切分种子，每个切分版本又应对应三种方法，不能错误地要求全局
  一一对应。

测试阶段：

- 每个“任务 × 方法 × 切分种子 × 模型种子”组合都使用一个全新且完全重置的容器；

- 运行器只删除精确控制 token；

- 过程片段表、\(K\)、训练展示表、两套切分表、模型保存规则、提示词、运行器和训练
  配置的哈希及冻结时间，都早于第一次正式测试生成；

- 除训练前的来源追溯外，参考程序结构分析只能在上述内容全部冻结后进行。

## 16. 其他可以考虑的场景

| 场景 | 能补充什么 | 为什么不建议先做 |
|---|---|---|
| [AppWorld](https://aclanthology.org/2024.acl-long.850/) | 多应用、自由写 Python、按最终状态评分 | 环境和训练解答更复杂，小模型成本高 |
| [APPS](https://arxiv.org/abs/2105.09938) | 证明方法不局限于 agent；可对 Python 语句组合学习过程片段 | 没有多轮环境反馈 |
| [SWE-Gym](https://github.com/SWE-Gym/SWE-Gym) | 定位、修改、测试等阶段边界很不明确 | 小冻结模型容易出现低成功率，容器成本高 |
| [WebLINX](https://github.com/McGill-NLP/weblinx) | 网页轨迹中的阶段边界不明确 | 许多指标仍偏向下一动作预测，最终状态评价不统一 |

如果 InterCode 工程上无法运行，APPS 可以作为非 agent 的备选实验，但它只能回答
“方法不局限于工具调用”，不能回答“在交互式 agent 中能否工作”。

## 17. 论文中可以怎样写

只有主结果和上面的检查都通过时，建议写：

> 我们进一步在 InterCode-Bash 上测试 TapMem。该任务要求模型自由生成并执行 Bash，
> 训练数据没有过程名称或切分标注。我们只用 Bash 解析器确定不会破坏语法的基本命令
> 单元，再从去泄漏的 NL2Bash 训练程序中学习长度不固定、反复出现的命令组合。训练时，
> 我们在过程片段数量不变的前提下抽取不同切分点，并让 TokMem、带 EOC 的方法和
> TapMem 使用完全相同的切分。测试时不提供解析器、切分点、记忆编号或参考命令，最终
> 按环境任务成功率评分。

随后填入真实的成功率、置信区间和失败案例。

不要写：

- “我们发现了真实步骤边界”；

- “TapMem 精确求和了所有隐藏切分”；

- “结果已经证明方法适用于任意开放世界 agent”。
